# ADR 0009：统一开发规范与契约基线

日期：2026-10-24。

状态：本次形成的文档设计基线，后续开发默认遵循；尚未配置工具或实现 API。编号 0002–0008 沿用开发步骤中的预留主题，本文不占用它们。

## 背景

用户要求在开发前设计统一规范，避免后续命名、接口响应、目录、状态处理和验收方式分散。已有 AGENTS.md 定义硬性边界，开发步骤定义阶段，但日常工程细则尚缺少单一入口。

## 决策

1. 增加 `docs/standards/development.md` 作为工程细则唯一入口，AGENTS.md 保存硬约束并链接它，开发步骤引用该规范。产品语义仍由产品文档和对应 ADR 决定。
2. 提供功能规格和验收模板；较完整功能使用模板，小范围文案/格式变更允许简写。当前不配置 CI/CD，不以文档模板引入外部审批系统。
3. HTTP 采用 `/api/v1`、JSON snake_case、单资源直接返回 DTO、集合 items/pagination、统一错误结构。MVP 默认 offset 分页和稳定排序；更新以 version/expected_version 表达并发冲突。健康检查独立，不提前注册未来功能路由。
4. OpenAPI 3.0.3 作为接口契约，S0 建设并按当期功能扩充；前端契约类型由同源契约同步，不复制 Inbox/Today 专用任务模型。生成工具在 S0 评估，当前不引入依赖。
5. 明确 app/ports 与 repo 的接口实现方向，事务与 Activity 遵守 ADR 0001；前端通过 features 分域、共享基础组件、语义 token、统一 API 客户端和缓存规则保持一致。
6. 工具链、ID 算法、认证、业务确认策略、可靠事件具体结构和 P1 安全方案仍按各阶段决定；统一规范不冒充这些产品或实现结论。

## 取舍与替代方案

| 方案 | 评价 |
|---|---|
| 仅规定格式/lint | 成本低，但不能解决接口、目录、缓存和交付不一致；不作为完整方案 |
| 每个领域单独选择目录和契约 | 局部灵活，但联调和跨页面操作需要不断转换；不采用 |
| 一个统一规范 + 按需规格/验收 | 作为本次方案，约束关键边界，局部实现仍可自行选择 |

Offset 简单且适合 MVP，但不是一致性快照；高频变动列表在变更后刷新，未来有需求时单独设计 cursor。前端 JSON 保留 snake_case 减少全量模型转换，局部变量/props 保持 TS 惯例。OpenAPI 带来同步维护成本，由接口变更验证和同源类型降低漂移，不提前建设复杂代码生成框架。

规范过细可能增加文档负担，因此简单变更允许简写；规范漂移通过 AGENTS/开发步骤链接、变更时同步维护和本地验收检查处理，不宣称已具有自动拦截能力。UI 先统一组件和 token 的使用规则，首个真实页面再定最终视觉值。
