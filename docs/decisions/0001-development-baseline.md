# ADR 0001：开发环境与本地验收基线

日期：2026-10-24

状态：环境约束已确认；实施细节作为后续 S0 的验收基线。本文记录开发约定，不代表环境已连通或功能已实现。

## 背景

PlanFlow 目前只有仓库约定和初始 Go module。用户已部署 PostgreSQL、Redis，当前不采用 CI/CD。原开发步骤仍以本地 Compose 和 CI 为前提，并存在事务分层、迁移顺序与审计建设时机的问题。

## 决策

1. 日常开发优先连接已有 PG/Redis，通过环境变量注入配置。开发、集成测试、实际使用的数据必须隔离；禁止测试清理共用库或共用 Redis。具体地址和账号在接入时配置，不写入本文。
2. 当前不建设 CI/CD。保留 lint、单元测试、集成测试、E2E、构建检查，由开发者在本机手动运行；阶段验收保存命令、结果与已知限制。可选 Git hook 不能代替验收，也不作为当前建设任务。
3. Testcontainers 是本机可运行的测试工具，与 CI/CD 无关。优先使用锁定版本的临时容器；本机无 Docker 时可接独立测试 PG/Redis，并验证隔离后运行相同测试。缺少测试条件时记录阻塞，不把未执行标为通过。
4. MVP 不要求 RustFS、存储配置、凭据 KEK 或空的 storage/secrets 包。RustFS 和文件/凭据能力到 P1 再引入；本地 PG/Redis Compose 仅为可选开发环境。
5. Activity 与事务基础设施在 S1 首次业务写入时建设。app 定义不含 GORM 类型的事务接口，repo 实现事务及绑定到同一事务的仓储；GORM 句柄不进入 app。后续通知事件如需可靠投递，采用同事务持久化事件的方案，在对应 ADR 中确定细节。
6. 迁移入口明确为：加锁 → 前置 SQL → AutoMigrate → 后置 SQL → 解锁；P1 文件阶段再增加 ensure bucket。前置 SQL 处理旧表调整，后置 SQL 处理依赖新表/新列的约束及回填。SQL 带版本/校验和，失败不标记成功，非事务 SQL 单独声明。整个流程不保证一次事务全部回滚，需记录部分成功状态并支持恢复；不能假定 AutoMigrate 只做新增，须审查实际 schema diff。api/worker 不运行迁移。
7. 先稳定范围、权限矩阵、API 契约和并发语义，再逐个完成业务闭环。P1/P2 只列路线图，不提前创建表、接口、配置或前端占位。

## 影响与取舍

- 复用已有服务，减少本地部署工作；连接、版本兼容、ACL/TLS 和资源隔离仍需在 S0 验证。
- 本地验收无需 CI 平台，但依赖开发者主动执行；通过版本化命令入口及验收记录降低漏检概率，不能声称具有自动拦截能力。
- 前置/后置 SQL 避免新库初始化时 SQL 引用尚未创建的表；相应增加迁移器的状态管理和失败重跑测试。
- Activity 提前，后续业务不用再补审计；事务接口增加少量抽象，避免 app 与 GORM 耦合。
- 本次不决定认证实现、通知持久化结构、文件直传方式、凭据加密细节；这些决策分别在对应阶段实施前形成 ADR。

## 考虑过的替代方案

| 方案 | 处理 |
|---|---|
| 每个人必须本地部署 PG/Redis/RustFS | 不作为日常前置；已有 PG/Redis 可复用，RustFS 属于 P1 |
| 先部署 CI/CD 再开始开发 | 不采用，符合用户当前约束 |
| 所有测试直接连接已有开发库 | 不采用，清理、并发和定时任务容易影响真实数据 |
| 为简化事务把 `*gorm.DB` 传入 app | 不采用，违反分层约束 |
| SQL 全部先于 AutoMigrate | 不采用，新增表的后置约束/回填无法稳定初始化 |
